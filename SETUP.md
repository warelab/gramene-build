# Gramene release 70 build setup (colden / _70_116)

**Status: set up and building.** The open decision below is closed; the six repos are checked out,
the sorghum v11 pipeline has been propagated onto them, and the build is resuming. Day-to-day
documentation now lives in [`build/README.md`](build/README.md) and [`build/docs/`](build/docs/) —
**this file is only the record of how the release root was established.**

Source DBs verified on **colden** (read-only, `gramene_web`): **267** `*_core_70_116_*` cores,
compara **`ensembl_compara_plants_70_116`**, **24** `*_variation_70_116_*`.

## Open decision — CLOSED 2026-10-08

> *Original question:* port the `build/` pipeline onto the main-release config, basing the ETL repos
> on the `sorghum_v11` fixes plus a new `main_v70` config — versus integrating with the existing
> `gramene-meta` main-release process.

**Decided: port this pipeline.** The staged `build/` pipeline is what v70 uses. Four months of
guards, bug fixes and two design reversals accumulated on the `sorghum_v11` branches after v70 was
cut, and every one of them exists because something shipped, or nearly shipped, a silently wrong
index. Integrating with `gramene-meta` instead would have meant repeating those failures.

Carried over: the staged pipeline in full, the maize ZMY pathway fix, the `saved_search` restore
tooling, and expression attributes. Deliberately **not** carried over: the rsID variant layer, the
pan-site Ensembl REST endpoint, and MAKER/VEP — all SorghumBase-specific. `22_germplasm` is present
but outside `make all`, since its source is unavailable.

The propagation is recorded per-repo in the `pre-v11-propagation-*` tags and the commits after them.

## How the config dependency works — do not "fix" this

Each consumer repo depends on the config through a **local path**:

```json
"gramene-mongodb-config": "file:../gramene-mongodb-config"
```

An earlier draft of this file advised pointing each `package.json` at `#main_v70`. **Do not.** The
GitHub-branch pins are what this pipeline exists to get away from: the old `#sorghum_v10_fable` /
`#sorghum_v7` pins resolved to the *oryza7 / sorghum7* configs and would have silently built into
the wrong database. `00_preflight` checks the resolved symlink, not just the dependency string, so a
reintroduced pin fails the build rather than quietly retargeting it.

npm *copies* a `file:` dependency rather than symlinking it, so `05_install` forces the symlink back
after npm runs. If you ever run `npm install` by hand in a consumer repo, re-run `make 05_install`.

`ensembl_db_info.json` lives in `gramene-mongodb/` and carries the 267 cores + compara. **It is not
regenerated by the build** — one of the v11 commits would have overwritten it and destroyed this
267-core configuration, which is why that commit was deliberately skipped during propagation.

## Key differences from the SorghumBase v11 build

The main release is not the sorghum subsite:

- `gramene-mongodb-config` is on `main_v70` with `dbName='search'` → mongo **`search70`** (the
  sorghum build used `sorghum_v11`, `dbName='sorghum'`).
- Solr cores are **bare** `genes70`/`suggestions70` — no species prefix.
- `basePath` is **`/v70`**, and the ports are **10070/11070** (r69 serves `/v69` on 10069). The
  subsites use `/<species>_v<N>` on the 50000+ block.
- **0 anchor genomes.** `EXPECT_ANCHORS=0` is correct, not an unset placeholder.
- Ensembl REST is the **public plants** service, `https://rest.ensembl.org`. The local `:3000`
  registry resolves 0 of 267 genomes; the SorghumBase pan-site resolves 18.
- User gene lists come from the shared `userData1` alone, not the per-site `sorghum*` databases.

So release70 with this pipeline is a *port*: reuse the species-agnostic build code and
orchestration, but take the config from the main-release `search`/`main_v*` conventions.

## Build

```
cd build
make 00_preflight     # validates colden reachable + cores/compara/anchors == EXPECT_*
make all
```
